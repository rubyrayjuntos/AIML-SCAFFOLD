# R3.2 — Platform Foundation implementation plan

Status: **approved for execution 2026-08-18.** No Terraform has been written or applied under this plan yet — approval authorizes starting Step A only; each subsequent lettered step is its own separate plan/review/apply/verify boundary (see Implementation plan's execution-rhythm note).

Scope per ADR 0012: provision/adopt Databricks and Foundry on the primary subscription through the new `infra/platform_foundation/` Terraform root. **Not in scope**: Unity Catalog, vector indexes, churn workload migration (R3.4), functional auth proof (R3.3), OpenTelemetry instrumentation (R5), the `azmlops`/backend-storage-account questions R3.1 explicitly deferred.

## Explore findings

### A. Databricks target

- Resource type: `azurerm_databricks_workspace` (confirmed present in the installed azurerm ~>4.0 provider via `terraform providers schema -json`, not assumed from docs).
- Required fields: `name`, `resource_group_name`, `location`, `sku`. `sku` must be `"premium"` — Unity Catalog (R3.4) requires Premium tier, and upgrading tiers later is disruptive; choosing Premium now avoids a forced migration.
- `managed_resource_group_name` (optional) should be set explicitly for naming consistency, matching this repo's existing naming convention. Azure auto-creates this managed resource group and its contents (a VNet, an NSG, a DBFS-root storage account, and Databricks' own system resources) the moment the workspace is created — **Terraform does not and should not declare those internals**, only the `azurerm_databricks_workspace` resource itself. This is the concrete answer to "identities Azure creates automatically vs. identities Terraform must own."
- Unity Catalog prerequisites: **none belong in R3.2.** UC metastore assignment happens at the Databricks *account* level via the separate `databricks` Terraform provider (account-admin authenticated, distinct from `azurerm`), not the workspace-level `azurerm` resource. R3.2 provisions a Premium workspace capable of UC later; R3.4 does the actual metastore/catalog work.
- Region: existing primary-subscription infra is `eastus`. Confirm Azure Databricks availability in `eastus` before finalizing the resource block (no reason to expect it's unavailable — it's a common-tier region — but not yet explicitly re-verified against the live SKU/region availability API as part of this plan).
- Cost: the workspace resource itself is not the primary cost driver — compute (DBUs) is, and R3.2 provisions no compute/clusters, only the workspace shell. Premium vs Standard tier affects per-DBU pricing and feature availability, not standing cost of an idle workspace.

It is confirmed during controlled execution per resource, one at a time (see Implementation Plan, step C).

The acceptance condition for adoption is not "the import command succeeded." It is:

> Terraform accurately describes the resource Azure already has, without attempting to recreate, relocate, or materially normalize it.

This matters concretely for the `eastus2` location: if any provider default, module default, or careless variable substitution causes Terraform to want to change that value to `eastus` post-import, that is exactly the kind of unintended-mutation failure this plan exists to catch before it reaches apply.

### C. Identity/RBAC

Current state (live-verified): only one identity has any access to the Foundry resource — `RSwan@raycswanyahoo.onmicrosoft.com` (a personal human login, the currently-authenticated az CLI identity), holding `Foundry User` at the resource-group scope. **No service principal or workload identity has any access today.** R3.2 cannot assume otherwise.

Decisions for this plan:

- **Apply identity for `infra/platform_foundation/`**: reuse the existing bootstrap deployment identity (`gh-azure-ai-ml-ops-r1-dev-oidc`, the same GitHub-OIDC-federated service principal R1 already proved for governed applies) rather than creating a fourth identity. It needs, at minimum: `Contributor` on the target resource group(s) (to create the Databricks workspace; to manage/import the Foundry account, project, and deployments), and `Storage Blob Data Contributor` on the new state container (see D).
- **Runtime identity for the churn reference workload**: reuse the existing compute identity (`id-azure-ai-ml-ops-dev-compute`) rather than minting a new one, consistent with the one-compute-identity-per-reference-app pattern already established. This identity needs `Cognitive Services OpenAI User` (confirmed exact built-in role name) on the Foundry account for runtime chat/embedding calls, and whatever Databricks-side grant is needed to call the workspace (exact scope TBD at R3.3, since that's identity *proof*, not just RBAC declaration).
- **Minimum Foundry roles** (confirmed via `az role definition list` against this subscription): `Cognitive Services Contributor` (management-plane, apply identity) and `Cognitive Services OpenAI User` (data-plane, runtime identity).
- **Minimum Databricks/Azure-side roles**: `Contributor` on the resource group for the apply identity to create the workspace. Databricks *account-level* admin rights (a separate concept from Azure RBAC, needed for Unity Catalog account-level setup) are explicitly **not** acquired in R3.2 — that's R3.4's concern.
- **Platform-administration grants vs. runtime-consumer grants**, made explicit rather than left implicit: `Contributor`/`Cognitive Services Contributor` on the apply identity are administration grants (create/manage the resources); `Cognitive Services OpenAI User` and the eventual Databricks data-plane grant on the runtime identity are consumer grants (use the resources). These are declared as two distinct role assignment blocks in Terraform, never merged into one identity's grant set.

**Explicit boundary (per your instruction): R3.2 declares/provisions these identities and RBAC. It does not claim they work.** No token is exchanged, no API call is made, no live authentication path is exercised as part of this plan. That proof is R3.3's entire job.

### D. Backend/state

- New container: `aiml-platform-foundation` (neutral naming, matching ADR 0012's rationale — not "shared" or "enterprise"), in the existing shared backend storage account `stazmlops0001devtf` (`rg-azmlops-0001dev-tf`). Key: `platform-foundation/dev.tfstate`, mirroring the bootstrap's own `key` structure (`infra/backend.tf`'s container is per-project; this key is per-environment within the new container, leaving room for a `prod` key later without a second container).
- Container creation is a **bootstrap-owned** concern, consistent with ADR 0001 ("Terraform state backends... are bootstrap prerequisites supplied by platform administration") and with `infra/modules/azure_foundation`'s existing job of creating `azurerm_storage_container.state`. R3.2 extends that module (or adds a parallel resource in the same module) to create the new container, rather than creating it out-of-band via `az` CLI the way the very first R1 container was bootstrapped before its own backend existed.
- Read/write on the new container: `Storage Blob Data Contributor`, scoped to the new container specifically, granted to the `platform_foundation` apply identity — mirrors `azurerm_role_assignment.backend_data`'s existing pattern exactly.
- State-conflict confirmation (done, see Explore method): `terraform state list` against the bootstrap `infra/` root shows only bootstrap resources (RG, storage container, role assignments, Entra app/federated credential/service principal, GitHub repo/environment/secrets) — no Databricks or Cognitive Services resources. `infra/terraform` has no real state at all; it is a syntax-validation-only CI fixture (`resource_group.target = "replace-me"`), not a deployed root. Neither existing root owns anything R3.2 would touch.

- The Foundry account and its two deployments must not be recreated — import only.
- No existing Azure ML resources (`rg-azure-ai-ml-ops-dev` and contents) are touched.
- No workload migration onto the new Databricks workspace (R3.4).
- No Unity Catalog or vector index recreation (R3.4).
- No `azmlops` retirement action (open decision, not scheduled).
- No backend-storage-account redesign — new container in the existing account only.

## Implementation plan

Organized by create / adopt / grant / verify, not by file.

**Execution rhythm: each lettered step below is its own governed plan → review → apply → verify boundary, not one bundled authorization.** Specifically: Step A (bootstrap's backend-container addition) is reviewed and applied on its own, through the *existing* bootstrap root, before `infra/platform_foundation/` is even initialized. Step B (Databricks) is a separate plan/review/apply/verify cycle after that. Step C (Foundry) is four *more* separate cycles, one per resource, per the progressive-adoption gate below. "Create backend, initialize new root, create Databricks" must never collapse into a single apply just because they're adjacent in this document.

**A. State foundation**
1. Extend `infra/modules/azure_foundation` (or add a parallel resource) to create the `aiml-platform-foundation` container in the existing backend storage account.
2. Add `azurerm_role_assignment` granting the bootstrap/apply identity `Storage Blob Data Contributor` on the new container, matching `backend_data`'s existing pattern.
3. `terraform plan` against the *existing* bootstrap root (it's a bootstrap-owned concern per D above — this is the one piece of this plan that touches `infra/`, not `infra/platform_foundation/`), reviewed, then applied. This is its own complete governed cycle, finished and verified before step 4 begins.
4. Initialize `infra/platform_foundation/` against the new container/key, starting from local state per the same one-time bootstrap pattern `infra/backend.tf` used originally, then migrate to the remote backend. Initializing a new root is not itself a mutating operation, but nothing in `platform_foundation` is declared or planned until this is done.

**B. Databricks**
1. Declare `azurerm_databricks_workspace` (`sku = "premium"`, explicit `managed_resource_group_name`, `location = "eastus"`) plus whatever minimal `azurerm_resource_group` it lives in.
2. `terraform plan`, reviewed.
3. `terraform apply`.
4. Verify live: `az resource show` on the new workspace, confirm `provisioningState: Succeeded`, confirm the auto-created managed resource group exists with expected contents (VNet/NSG/DBFS storage), confirm workspace URL resolves.

**C. Foundry — progressive adoption, one resource at a time, not bulk import**

Bulk-importing all four resources and checking the plan once only answers "did Terraform accept the syntax." The actual question — does Terraform accurately describe what Azure already has, without silently trying to recreate, relocate, or normalize it — requires checking after *each* adoption, since a drift-causing default in one resource block shouldn't be allowed to hide behind three other imports' worth of noise in a single combined plan.

For each of the four resources, in order (account → project → `gpt-5` deployment → `text-embedding-3-small` deployment):

1. Model that one resource as a Terraform block using its exact live values from the Explore section above.
2. `terraform import <address> <live-resource-id>`.
3. `terraform state show <address>` — inspect what Terraform now believes this resource's state is.
4. `terraform plan`, scoped to what's been declared so far.
   - **Replacement proposed** → stop. Do not proceed to the next resource until reconciled.
   - **Unexplained drift** (any attribute Terraform wants to change that wasn't a deliberate declared choice) → stop. Reconcile against the live value before proceeding.
   - **Clean plan, or only the next-not-yet-declared resources showing as "to be created" exactly as expected** → continue to the next resource.
5. Only once all four resources are individually imported and each intermediate plan was clean does this step count as done.

This is the concrete execution of C1–C7 as specified in review, applied to each of the four resources rather than run once.

**D. Identity/RBAC**

Both identities already exist and already do other jobs (R1's deployment/OIDC identity, R1's compute identity). What R3.2 adds to each of them is a genuine expansion of responsibility, not a baseline grant to something new — call that out explicitly in the role-assignment resources' comments/naming when written, so a future reader of `infra/platform_foundation/` can see these are additive grants onto pre-existing, already-audited identities, not a fresh, unreviewed identity with unknown blast radius.

1. Declare the apply identity's grants: `Contributor` on the Databricks resource group, `Cognitive Services Contributor` on the Foundry account.
2. Declare the runtime/consumer identity's grants: `Cognitive Services OpenAI User` on the Foundry account for `id-azure-ai-ml-ops-dev-compute`. Databricks-side runtime grant is scoped at R3.3, not declared blind here.
3. Do not attempt any live auth exchange, token acquisition, or API call as verification — that's explicitly out of scope (R3.3). RBAC assignment succeeding is not evidence the identity can actually use it; only R3.3's live exercise is that evidence.

**E. Outputs/contracts**
1. Publish from `infra/platform_foundation/`: Databricks workspace ID and URL, Foundry account resource ID, Foundry endpoint(s), both deployment names/IDs.
2. Consumers (the churn reference app now, generated projects later) receive these through their own declared configuration (`scenario.yaml`/`settings.foundry_endpoint` etc.), populated from these outputs at generation/config time — **never via `terraform_remote_state` coupling one Terraform root to another's state.** This is the concrete mechanism that keeps the factory boundary intact if `platform_foundation` is ever reorganized later.
3. Non-functional requirement, carried from the roadmap decision: outputs must include the identifiers later needed for OpenTelemetry correlation (Foundry resource ID, Foundry deployment identity, Databricks workspace ID — Azure ML workspace ID and App Insights/Log Analytics IDs already exist from R1). No instrumentation is added now; this plan only avoids foreclosing it. No architectural choice in B or C above (naming, resource shape, identity model) should make later trace correlation harder than it needs to be.

**F. Evidence**
1. Reviewed, saved `terraform plan` output for both the state-foundation addition and `platform_foundation`'s own apply.
2. Import evidence: the exact `terraform import` commands run and their output, especially the post-import zero-drift plan.
3. Apply evidence: the Databricks workspace creation's plan/apply output.
4. Independent live-resource verification: `az resource show`/`az cognitiveservices account show` re-run after apply, compared against what Terraform believes state to be — the same discipline used throughout R3 Slice 1 and R3.1, not a new standard.

Recorded in `docs/scenarios/churn/demo-runbook.md` or a dedicated R3.2 evidence entry once execution actually happens — not written yet, since no apply has occurred.
